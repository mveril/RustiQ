RustiQ Manual

Command-line reference

Run these commands from any working directory with the installed rustiq binary. In a source checkout without an installed executable, replace the rustiq command prefix with cargo run --locked --. rustiq --help and rustiq <command> --help show the options supported by the installed build.

Manual

rustiq docs opens the offline HTML manual bundled with a release archive or Nix package. Cargo-only installations open the online manual. Use --web to force the online version, or --print-path to print the local index path or online URL without launching a browser. See installation for relocation, headless use, browser selection, and incomplete-installation errors. PDF export is not implemented.

Binary version and build details

rustiq --version (or rustiq -V) prints the package version on one line. Use rustiq --version --verbose (or rustiq -V -v) for grouped build details; the two flags can also appear in reverse order. These requests return exit code zero and write plain text to standard output. The top-level --verbose flag requires --version; basis list --verbose retains its existing meaning.

The detailed output groups source, compiler, CPU target, and build configuration metadata. It includes the full Git commit and status, compilation target, Rust compiler and LLVM versions, Cargo optimization level, exact profile when supplied by the build, declared debug-information, LTO, codegen-unit, debug-assertion, and integer overflow-check settings, target architecture and explicitly requested target CPU when available, enabled target features, and enabled Cargo features. The architecture is displayed whenever Cargo provides it, independently of whether a target CPU was explicitly requested. No named ISA classification is inferred from the features. Cargo’s synthetic default feature marker is omitted. Values that Cargo or the build system cannot establish are generally omitted from text output. The integer overflow-check row explicitly shows unknown when unavailable; without a declared value, debug assertions are read from the CLI’s compiled cfg(debug_assertions). Cargo’s PROFILE variable does not identify custom profiles reliably, so the profile is shown only when the build supplies its exact name. Release artifacts built by cargo-dist declare dist in their workflow; Nix package builds declare release.

Configuration declared in the selected package profile in Cargo.toml is labeled as declared. Profile inheritance is followed. Cargo does not expose effective LTO, codegen-unit, overflow-check, debug-assertion, or debug-information settings to build scripts. Declared values are reported when the selected profile declares them; debug assertions otherwise use the compiled cfg value and integer overflow checks show unknown. Cargo’s optimization value is supplied to build scripts; a separate compiler flag can override it. Target CPU is populated only from an explicit RustiQ build override or a recognized target-cpu option in Cargo’s encoded rustflags or RUSTFLAGS. The target feature list comes from Cargo’s target cfg for the final target; it does not describe runtime CPU support. Observed rustflags are not a complete record of compiler arguments or Cargo configuration.

LTO and codegen units are labeled as declared because Cargo does not expose their effective compiler values to build scripts. Target features describe compile-time target settings, not instructions supported by the machine at runtime. The architecture and globally enabled features come from Cargo’s final compilation target, including during cross-compilation. The display does not hard-code CPU families, instruction sets, ISA levels, or reference feature lists. This allows the same code to report targets supported by different compiler toolchains without assuming their naming conventions. Rust’s target cfg does not establish the minimum compatible processor for the entire linked executable, particularly if native dependencies or specialized kernels use additional instructions. RustiQ does not guess the concrete build-host CPU.

For example, the grouped output has this shape (unknown optional fields are omitted and the values depend on the build):

rustiq 0.1.0-alpha.1

SOURCE
  Git commit          <full commit hash>
  Status              dirty

COMPILER
  Rust                <compiler version>
  Channel             <stable, beta, nightly, or dev>
  Rust commit         <full hash, only for nightly when available>
  LLVM                <LLVM version>
  Target              <target triple>

CPU TARGET
  Architecture        <target architecture, when available>
  Target CPU          <explicit CPU request, when available>
  Target features     <features enabled for the compilation target, when available>

BUILD CONFIGURATION
  Profile             <exact profile, if supplied>
  Optimization        <Cargo value>
  Debug information   <profile value, if declared>
  LTO                 <profile value (declared)>
  Codegen units       <profile value (declared)>
  Debug assertions    <profile value (declared), or compiled cfg value>
  Integer overflow checks <profile value (declared), or unknown>
  Cargo features      <enabled features, excluding the default marker>

NUMERICAL LIBRARIES
  Linear algebra      nalgebra <version>
  Parallelism         rayon <version>
  Special functions   special <version>

CHEMICAL DATA
  Periodic table      mendeleev <version>
  Bohr radius         CODATA 2018

The numerical libraries section identifies nalgebra for linear algebra, Rayon for parallelism, and special for special functions used by the Boys function implementation. Their versions are read at build time from Cargo.lock when it contains a single distinct version of each crate; otherwise the corresponding version is shown as version unknown. When terminal hyperlinks are enabled, each backend name and version links to that exact version on crates.io. Unknown versions have no link. The parallelism row does not report the active thread count.

The chemical data section identifies the mendeleev crate used for chemical element properties; its resolved version is read from Cargo.lock during the build, using the same fallback and crates.io hyperlink behavior as the numerical libraries. The Bohr-to-ångström conversion factor in the core uses the CODATA 2018 Bohr radius from NIST. Its revision and NIST reference URL are defined alongside the conversion constant in rustiq-core, not duplicated in the CLI. With terminal hyperlinks enabled, the revision links to the NIST CODATA 2018 table. This does not claim that all chemical constants, atomic masses, or basis sets use CODATA 2018. Basis sets and their own revisions are specific to individual calculations and are not reported in this binary-version output.

Integer overflow checks concern integer arithmetic, not floating-point NaN, infinity, or SCF convergence.

Text calculation banners show a 12-character commit abbreviation and its source state. When Git provenance is unknown, they show Build: unknown. OSC 8 links, when enabled, target the complete commit hash. JSON calculation output remains free of banners and retains its existing schema.

All fields are embedded during compilation and remain available when the executable is copied elsewhere, without Git or Rust installed. The source state is clean or dirty according to changes to tracked files at build time; untracked files do not affect this Git dirty flag. The Status row displays clean, dirty, or unknown; a missing commit is displayed as unknown, as can happen when compiling an unpacked source archive without Git metadata. When stdout is a terminal that supports hyperlinks, the Git commit hash links to that commit in the RustiQ repository. The target feature list links to the Rust Reference’s explanation and tables of processor features. Redirected output stays plain text unless FORCE_HYPERLINK explicitly enables links. These fields describe build provenance, not a cryptographic identity of the executable or proof that two builds are identical. The compiler commit is shown only for nightly toolchains, when available; stable, beta, and dev builds still show their compiler channel.

Packagers may set RUSTIQ_BUILD_GIT_COMMIT to a full Git hash (or unknown) and RUSTIQ_BUILD_GIT_STATE to clean, dirty, or unknown at compilation time to override Git discovery. An injected commit without an injected state uses state unknown. RUSTIQ_BUILD_PROFILE, RUSTIQ_BUILD_SYSTEM, and RUSTIQ_BUILD_TARGET_CPU can supply exact build-system metadata when known; the profile, system name, and CPU values are validated before embedding. Nix supplies its profile, build-system name, and flake revision, while the cargo-dist release workflow supplies its profile and build-system name. The Nix source revision is the Git revision passed by the flake, not a Nix store path. Setting these variables when running an already built binary has no effect.

Commands

Manual pages and shell completions

Cargo builds enable the independent manpages and completions features by default. They provide these commands:

rustiq manpages ./manpages
rustiq completions > current-shell-completion
rustiq completions bash > rustiq.bash
rustiq completions zsh > _rustiq
rustiq completions fish > rustiq.fish
rustiq completions elvish > rustiq.elv
rustiq completions powershell > rustiq.ps1
rustiq completions nushell > rustiq.nu

manpages creates its destination directory and replaces existing generated pages. When switching between standalone and packaging modes in the same directory, obsolete rustiq-manpages.1 and rustiq-completions.1 pages are removed. Use a fresh directory for a completely clean generated set if other commands have changed between RustiQ versions. It writes rustiq.1 and pages for the subcommands, including nested commands such as rustiq-artifact-inspect.1. Each page includes the online manual in its SEE ALSO section. completions writes only the script to standard output; generation errors go to standard error and return a failing exit status. Its shell argument is optional: RustiQ recognizes the calling process’s shell first, then falls back to the SHELL environment variable. This includes nu for Nushell and pwsh or powershell for PowerShell. If neither identifies a supported shell, the command asks you to provide one explicitly. Supply the argument when running through a launcher that obscures the calling shell. Both generators reflect the commands and options enabled in the current build. For example, offline builds omit online-only basis commands. By default, generated files also include manpages and completions when those features are enabled. Set RUSTIQ_PACKAGING=true (or 1) to omit manpages and completions from both manuals and shell completion scripts; false, 0, or an unset variable keeps them. Other packagers can use this setting when installing generated files alongside a binary built without the generator features. Values other than true, false, 1, and 0 produce an error.

Load the generated file in the matching shell: source ./rustiq.bash in Bash, source ./rustiq.fish in Fish, or source ./rustiq.elv in Elvish. For Zsh, place _rustiq in a directory on $fpath before running autoload -Uz compinit; compinit. In PowerShell, dot-source the script with . ./rustiq.ps1; it registers native argument completion without adding a command wrapper or Get-Help integration. In Nushell, load it with use ./rustiq.nu *. Add the appropriate loading command to your shell configuration to retain it in future sessions.

To select features explicitly from a checkout, use, for example:

cargo run --locked --no-default-features --features manpages -- manpages ./manpages
cargo run --locked --no-default-features --features completions -- completions nushell

These examples omit online; add it to the feature list if needed. A build without a generator’s feature omits that command and its dependency. The Nix package installs the generated assets but disables both generators in its executable.

run options and input selection

The input filename extension selects TOML, Nickel (.ncl), or a portable .rustiq bundle. TOML describes a single calculation. Nickel can describe one calculation or an ordered array; an array of one uses the single-calculation output contract, while a larger array uses the batch contract. A .rustiq input reconstructs and reruns its archived resolved calculation(s); multi-entry bundles use the batch contract. Nickel imports resolve relative to the importing file. Geometry paths resolve relative to the top-level input file; for TOML read from standard input, they resolve from the current working directory. Direct archive reruns cannot be combined with --reuse, --artifact, --cache-dir, --auto-download, or --no-auto-download; the source bundle is read-only and provides its resolved basis and inputs. Archive reruns do not use the local ERI cache or basis-download settings. Text output shows SCF progress; JSON output suppresses progress and writes only the result document.

Important options:

OptionBehavior
--format FORMAT (text or json)Select text output (default) or versioned JSON. JSON result data is written to standard output.
--prettyPretty-print single-calculation or batch JSON, optionally with syntax highlighting. Requires --format json.
--color MODE (auto, always, or never)Control ANSI colors globally; also accepts RUSTIQ_COLOR. Use --color never when redirecting pretty JSON.
--auto-download / --no-auto-downloadIn online builds, allow or disable fetching a missing basis for this run. These override RUSTIQ_AUTO_DOWNLOAD; without either flag, 1 or true (case-insensitive) enables it and other or missing values disable it. Offline builds always use local bases.
--cache-dir DIRChoose the AO ERI cache root for this run. The input must also set [cache].enabled = true; this option does not enable caching.
--reuse PATHRead a portable .rustiq bundle and reuse the first compatible AO ERI for each calculation.
--artifact PATHWrite the current calculation or batch as a portable .rustiq bundle, independently of text or JSON output.

Output presentation is selected exclusively by the CLI --format text|json option. The TOML and Nickel calculation contracts do not accept an output section. Scientific execution emits a completion event after all requested stages complete. An HF-only result can be unconverged and still be a completed execution. The CLI consumes it to retain a lightweight summary, then selects text or JSON presentation after execution. JSON retains its single versioned result document (including the existing batch envelope), without streaming intermediate events. The campaign runner returns ordered outcomes directly; recoverable failures remain in that result and fatal orchestration failures stop the campaign before rendering.

The cache directory path is resolved from the caller’s current working directory. Pass the same --cache-dir to cache list or cache remove to manage entries from a run that used a custom cache root.

The CLI reports input, basis, preparation, and calculation errors as diagnostics. Exit codes follow the Unix convention: zero means complete success; any nonzero code means the command did not fully succeed. Codes 3 and 4 are RustiQ-specific.

CodeMeaning
0All requested calculations succeeded. Help and version requests also return zero.
1General error, a batch with no successful calculations and at least one error unrelated to HF non-convergence, or a fatal infrastructure error.
2Invalid command-line arguments.
3No requested calculation succeeded, and every unsuccessful calculation stopped because HF did not converge.
4A completed batch contains both successful and unsuccessful calculations, including non-convergence or recoverable errors.

These codes apply to TOML, Nickel, and .rustiq inputs, with text or JSON output. A calculation succeeds only when the complete requested method succeeds: converged HF followed by an MP2 error is not a successful calculation. MP2 blocked by HF non-convergence counts as non-convergence, so a single such run returns 3. Input validation before execution returns 1; CLI argument validation returns 2. Fatal infrastructure errors during execution or output writing return 1 and can prevent result JSON from being produced. Artifact publication happens after successful scientific execution. If publication then fails, the CLI still writes the completed calculation or campaign JSON before returning 1; this behavior is covered by publication_error_keeps_complete_calculation_and_batch_json.

A single HF-only calculation that reaches its iteration limit still returns its final-iteration result, with converged: false in JSON, but exits with 3. MP2 requires converged HF; a single MP2 run blocked by non-convergence reports a diagnostic without result JSON. Recoverable per-entry errors in a batch do not prevent later entries from running. The batch JSON records each outcome, and a valid JSON document can accompany a nonzero exit code. Output fields remain defined by the versioned schemas. Convergence alone does not establish the physical validity of a result.

From the repository root, capture the status even when the calculation fails (the conditional also works in shells using set -e):

status=0
cargo run -- run samples/h2/sto-3g/calculation.toml --format json > result.json || status=$?
printf 'Exit code: %s\n' "$status"

When using the installed binary, replace cargo run -- with rustiq. In scripts, inspect the exit code and, when available, individual JSON outcomes; see the JSON guide.

Calculation input contracts

TOML and Nickel inputs use the same calculation settings. The embedded Nickel contracts are authoritative for defaults, allowed fields, types, and validation; the CLI does not define a separate TOML-only set of defaults. Consult the TOML guide for sections and checked-in examples, then the geometry, Hartree–Fock, and MP2 guides for the corresponding scientific settings. The Nickel contracts and their validation are linked from the reference index.

The following settings are accepted by both TOML and Nickel. This is a navigation aid, not a second schema: exact defaults, value constraints, and cross-field validation remain defined by the linked Nickel contract.

SectionSupported settings
[molecule]geometry, charge, multiplicity, units (Angstrom or Bohr)
[basis]name
[method.hf]method (Auto, Rhf, Uhf), max_iterations, convergence_threshold, guess, diis.enabled, diis.max_history, orthogonalization.linear_dependency_threshold
[method.mp2]frozen_orbitals, memory_limit
[integrals]schwarz_threshold for integral screening
[cache]enabled for the disposable local AO ERI cache

The accepted density guesses and their fields are defined in the Nickel contract; see the HF guide for their use. The cache stores AO ERI data only; it does not store Hartree–Fock or MP2 results, and a cache hit does not guarantee that every calculation will run faster.

Cache and portable bundles

The local AO ERI cache (atomic-orbital electron-repulsion integrals) is a disposable optimization for deterministic two-electron integrals. It is disabled by default in the calculation input; --cache-dir only selects where enabled cache entries are stored. Use cache list and cache remove to inspect or remove entries. Missing, invalid, or incompatible entries are recomputed. The local cache is not a deliverable or a portable calculation file.

Portable .rustiq bundles use the V1 ZIP/ZIP64 format described by the authoritative persistence specification. The format is conceptually inspired by EZFIO in Quantum Package 2 (qp2), but uses an independent archive structure and APIs; see the comparison. For a guided create, inspect, and reuse workflow, see the portable bundle guide. Bundles are separate from the disposable local AO ERI cache. Reuse opens its source read-only. For each requested calculation, RustiQ selects the first compatible, supported AO ERI in bundle order; when none is available, an enabled local cache is checked before recomputation. A corrupt selected payload is an error. A source entry can supply data to multiple calculations in a Nickel batch.

rustiq run samples/h2/sto-3g/calculation.toml --artifact h2.rustiq
rustiq run samples/h2/sto-3g/calculation.toml --reuse h2.rustiq --artifact next.rustiq --format json
rustiq artifact inspect h2.rustiq --format json
rustiq artifact verify h2.rustiq
rustiq run h2.rustiq
# Replace the source bundle after all requested calculations produce results:
rustiq run samples/h2/sto-3g/calculation.toml --reuse h2.rustiq --artifact h2.rustiq

Publication captures the current requested calculation collection and its compatible known artifacts. It does not append history. An existing destination is accepted only when it resolves to the explicit --reuse source; otherwise the command fails without replacing it. Publication happens after every requested calculation produces a result. Preparation or execution errors prevent publication of the collection and leave the destination unchanged. An HF-only non-converged result can contribute its AO ERI. A Nickel batch containing only non-converged HF-only results can publish its bundle even though the command exits unsuccessfully. If MP2 was requested but HF does not converge, execution fails and the bundle is not published. HF orbitals, SCF restart state, DIIS history, and MP2 results are not persisted.

When --reuse or --artifact is used, JSON calculation results include an optional artifacts array. decision reports archive selection (reused, missing, or incompatible); origin reports the ERI actually used (archive, cache, or computation). A reused item includes its zero-based source_index. Without these options the existing JSON result shape is retained. run FILE.rustiq --format json uses the regular single-calculation or batch result schema but does not include this reuse-decision array: the bundle is the implicit artifact source for that mode. Publication failures are reported on stderr and return a failing exit status. Since publication follows scientific execution, JSON for the completed calculation or campaign is written before that publication error is returned.

artifact inspect PATH displays requested and resolved scientific snapshots, producer details, artifact representations, and captured source names and sizes. In text mode, canonical TOML and XYZ are syntax-highlighted when color is enabled by --color or RUSTIQ_COLOR; JSON output remains structured JSON. It validates the archive index, provenance, snapshots, and declared artifact sizes, but does not hash or decode numeric payloads. Use artifact verify to check supported payloads eagerly; otherwise, execution checks a payload when its scientific stage selects and reads it. Inspection does not execute calculations or establish scientific validity. JSON output follows the artifact inspection V1 schema. artifact verify PATH eagerly reads and validates supported numerical payloads. It currently checks compact AO ERI payload hashes, NPY encoding, array dimensions, and consistency with the declared AO basis. It reports an error for an invalid payload or unsupported representation. Verification does not run a calculation or establish scientific validity. The archive captures exact bytes of the main input and geometry files as shared provenance; it does not capture Nickel’s full import graph. See the persistence specification for the archive contract and API details.

Output contracts

run --format json selects one of two versioned contracts: the single calculation schema or the batch schema. schema_version identifies the contract; schemas, rather than this manual, define the complete field sets. The JSON guide describes output selection, standard output behavior, failure cases, and the existing automated checks.
